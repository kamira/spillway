### 決策 3、4、6 的指令與測試規則

① 首次鎖定(決策 3;只有本筆使用 `-c freeze`,讓版本等於已查核的 venv):

```bash
uv pip freeze --python .venv/bin/python --exclude-editable > "$TMPDIR/spillway-freeze.txt"
uv pip compile pyproject.toml --universal --python-version 3.11 --generate-hashes --no-header --no-annotate \
  -c "$TMPDIR/spillway-freeze.txt" -o requirements.lock
uv pip compile pyproject.toml --extra dev --universal --python-version 3.12 --generate-hashes --no-header --no-annotate \
  -c requirements.lock -c "$TMPDIR/spillway-freeze.txt" -o requirements-dev.lock
uv pip compile build-constraints.in --universal --generate-hashes --no-header --no-annotate -o build-constraints.lock
```

② 升版重產(決策 6 ②;macOS 寫法,Linux 把 `date` 換成 `date -u -d '7 days ago' +%Y-%m-%dT%H:%M:%SZ`):

```bash
CUT="$(date -u -v-7d +%Y-%m-%dT%H:%M:%SZ)"
uv pip compile pyproject.toml --universal --python-version 3.11 --generate-hashes --no-header --no-annotate \
  --exclude-newer "$CUT" --upgrade-package <name> -o requirements.lock
uv pip compile pyproject.toml --extra dev --universal --python-version 3.12 --generate-hashes --no-header --no-annotate \
  --exclude-newer "$CUT" -c requirements.lock -o requirements-dev.lock
# 只有 setuptools 要升時才改 build-constraints.in,再以 ① 最後一行(含 --no-annotate)重產 build-constraints.lock
```

(`<name>` 是 README 指令中由擁有者代入的套件名;全面升版時把 `--upgrade-package <name>` 換成 `--upgrade`。)

③ 合約測試 `tests/contract/test_dependency_lock.py`(只讀檔,與環境無關):

| 類別 | 命中 | 說明 |
|------|------|------|
| new-dependency | 否 | 不新增、不升級相依;只把既有相依鎖到目前版本。setuptools 是既有建置後端,只把隔離建置已選用的 84.2.1 加上雜湊(決策 9);平台限定套件(決策 3)是既有相依在 Linux、Windows、py<3.12 的傳遞相依,不安裝於 macOS venv;新腳本只用標準庫 |

| irreversible-delete | 否 | — |
| prod-migration | 否 | — |

已知限制:

1. lock 只保護以 lock 安裝的環境;雜湊只證明「與鎖定時下載的檔案相同」,不證明鎖定的版本本身無害(以本次查核與升版流程補足)。
2. 漂移偵測(`tests/unit/test_venv_matches_lock.py`)不是完整性保證;完整性靠 `scripts/check_venv_integrity.py`,而它只能在 `.pth` 被觸發之前、以 `-I -S` 執行時才可信。
3. 不加 `--no-build` 時,竄改 wheel 雜湊會退回 sdist 建置(仲裁 P7),所以安裝一律加 `--no-build`。他平台若缺 wheel,安裝會失敗,不會改走建置。
4. `!=` 只擋已知的三個版本,不擋未知版本,也不擋傳遞相依;不經 lock 的安裝(`pip install .`、`uv tool install .`)沒有雜湊保護。
5. 平台限定套件(決策 3)與 Python 3.11 的 runtime 環境沒有在驗收中涵蓋。驗收在 macOS 執行;3.11 只做 runtime lock 的安裝與 `import spillway` 探測(T1 L2)。
6. Playwright 的瀏覽器從 CDN 下載,沒有雜湊驗證;uv 本身的版本沒有釘住(記錄為 uv 0.13.5)。
7. 驗收時若以離線方式安裝,依賴本機 uv 快取,不證明 PyPI 來源可用。
8. 冷卻期 7 天能避開「上架數小時內被撤下」這類事件,擋不住潛伏更久的惡意版本。
9. 入侵檢查只對照 RECORD,目的是抓已知的 `.pth`/`sitecustomize` 啟動掛鉤與安裝後的檔案修改,不防已能任意寫入 venv 的人:重算 RECORD 雜湊、新增整個 dist-info 都能繞過(dist-info 的名稱與版本未對照 lock,施工審議 F9 未做);`__pycache__` 內偽造的 `.pyc` 不會被發現;那個人也能改腳本本身。
10. 漂移偵測不求值 marker:有 marker 的套件即使本機應該安裝,沒裝也不會被發現;spillway 不論安裝來源都略過。
11. 省略 `--build-constraint` 的 `-e .` 安裝,setuptools 由索引解析、沒有雜湊驗證;README 的指令都帶這個旗標(施工審議 P-a)。
12. 合約測試的解析器是格式檢查,不是拒裝機制;版本與 marker 群組已收緊(施工審議 F10),但不是完整的 PEP 440 檢查。實際拒裝由 `uv --require-hashes --no-build` 負責。
13. Python 3.11、3.12 上,CLI 成員的子行程留下仍持有 stdout/stderr 的孫行程時,`CliRunner` 會等到逾時才結束(`asyncio.subprocess.Process.wait()` 在這兩版會等管線關閉;M3a 既有缺陷),直到修正 CHG 合入(決策 10)。開發 venv 用 3.13 不受影響;3.11 的 runtime 環境受影響。

### 風險與回滾

| 風險 | 影響 | 對策 |
