## 動機

CHG-20261107-01 以 Python 3.12 新 venv 跑全量測試時,`tests/unit/adapters_base/test_cli_runner.py::test_grandchild_holding_stdout_bounded_drain_after_normal_exit` 失敗(3.13 通過)。(決策審議修訂 AM-1)以最小探針重現:在 Python 3.11、3.12 上,於子行程結束**前**登記的 `asyncio.subprocess.Process.wait()`,要等到 stdout/stderr 管線全部關閉才返回;`returncode` 則由 child watcher 及時設定,與管線無關(3.13 改在 `_process_exited` 時就喚醒 waiter)。於是:

1. 子行程正常結束,但同 group 的孫行程仍持有 stdout(例如 CLI 的 hook 或背景 shell),`CliRunner.run` 會等到 `timeout`,把一次成功的呼叫記成 `timed_out=True`、`killed_reason="timeout"`。adapter 會因此丟掉已收到的輸出,帳本記成 `error`,latency 等於整個 timeout(預設 600 秒),tokens 與 cost 為 None。`max_concurrency=1` 時,這個成員在這段期間一直佔著名額,其他請求只會拿到 `concurrency_full`。
2. 停機(`terminate_all`)時,若有逃出 group 的孫行程仍持有管線,`run` 會等到它自己的 timeout,並記成 `timeout`,而不是 `shutdown`;`timeout=None` 時要等到孫行程自己結束。
3. 走終止路徑(逾時、取消、停機)時,若有逃出 group 的孫行程仍持有管線,SIGKILL 之後的回收等待(`cli_runner.py:338`)每次會多等 `max(1.0, term_grace)`,預設 5 秒。

NFR-7 承諾 Python 3.11 以上;擁有者目前的 venv 為 3.13,不受影響。

另外,3.12 全量閘還有 4 個與 CliRunner 無關、但前景與背景都必定失敗的 `tests/fakes/test_cli_upstream.py` 測試(3.12 的 `Popen.communicate()` 對已關閉的 stdin 執行 flush,丟出 `ValueError`);CHG-20261107-01 把這 4 個失敗誤記為 SIGINT 測試。兩者一併在本筆處理(決策 7,決策審議仲裁 #1、#2)。

## 使用者故事

1. 作為擁有者,我要在 Python 3.11、3.12 上使用 CLI 成員時,子行程正常結束就立即回應,不因孫行程持有 stdout 而等到逾時(NFR-7;`cli_runner.py` 模組說明與 design `CliRunner` 列:「主行程結束後最多再等 `drain_timeout`」)。(決策審議修訂 AM-1)

已知限制(決策審議修訂 AM-10):

1. 3.11 只以探針驗證 CliRunner 的孫行程情境,不跑全量測試(dev lock 需 3.12 以上)。
2. Linux、Windows 未涵蓋。
3. 子行程恰好在期限當下結束時,可能得到 `exit_code=0` 加上 `timed_out=True`(watcher 延遲毫秒級;既有行為)。
4. Linux 上使用 3.12 的 Pidfd watcher、而且事件迴圈已停止時(atexit),`kill_all_sync` 遇到未回收的 zombie 會等滿 grace(既有行為,未驗證)。
5. 殘留的孫行程被終止時,`killed_reason` 仍為 None,帳本看不到這件事(既有設計)。

## 修改指引

### 目標
