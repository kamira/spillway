## DIR-1 — 審議採最簡化機制:審議席只給位置與意見,獨立審議席統整裁決
- 日期 / 分支:2026-10-29(UTC+0)/ all
- 情境:任何需要審議的時點(CHG 決策審議、逐 task review、整支 branch review)。
- 規則:
  1. 席數取該風險等級允許的最少席數;不額外加席,不做第二階段交叉互讀(高風險除外,見下方「與預設的差異」)。
  2. 每個審議席只輸出「程式碼位置(`path:line`)+ 意見」清單,不下 pass/fail 裁決、不做彼此權衡。
  3. 最後由一個**獨立審議席**統整:它未參與該筆實作、也不是提出意見的任何一席;逐條權衡意見(採納/不採納 + 理由),並給出唯一的最終判決。判決與取捨理由寫進 CHG。
  4. 永遠停點(不可逆刪除、付款、正式資料遷移、安全邊界變更)不受本條影響,照舊停下交人。
- 與預設的差異(已揭露):預設中風險 ≥5 席、高風險全席 + 兩階段交叉驗證,且 risk/security/compliance 席 fail 具否決權;本條改為意見制,否決權集中在獨立審議席。autopilot runner 的程式碼審查面板有硬下限(中/高風險 3 席,`--review-panel` 不能調低),跑 runner 時以 runner 下限為準,再交獨立審議席統整。
- 原因:使用者指示審議以最簡化機制進行。
- 信度:使用者確認
- 狀態:生效

## DIR-2 — 威脅模型不含外部有權限者;安全審議只做有限檢查
- 日期 / 分支:2026-10-29(UTC+0)/ all
- 情境:安全審議、security 席、CHG 的「安全影響」節。
- 規則:
  1. 威脅模型假設僅擁有者本人在本機使用(見 README「使用範圍」與 docs/spec.md 1.1.1),不分析外部使用者、多租戶、權限角色、對外暴露的攻擊面。
  2. 安全審議只做以下有限檢查:(a) 永遠停點四類是否被觸及;(b) 秘密(API key、token)不寫入 repo、log、context 記錄;(c) 不讀取、不轉發訂閱 OAuth token(docs/spec.md 1.1.2)。
  3. 範圍外的安全議題只記為意見,不阻擋。
- 與預設的差異(已揭露):永遠停點與高風險 CHG 的「## 安全影響」四類盤點由治理層硬性要求,本條不放寬它們;放寬的是額外的威脅分析深度。
- 原因:使用者指示不考慮外部有權限使用,安全審議採有限方式。
- 信度:使用者確認
- 狀態:生效

## DIR-3 — 每種 AI 是一個自含的 adapter 模組,自帶可用模型清單;後台以選單選取
- 日期 / 分支:2026-10-29(UTC+0)/ all
- 情境:新增或修改任何供應商/AI 的接入;成員建立與編輯畫面。
- 規則:
  1. 一種 AI 一個子套件 `src/spillway/adapters/<module>/`(`MANIFEST`、`create()`、`adapter.py`、`models.yaml`、`README.md`),啟動時自動發現;新增 AI 不修改任何既有檔案,模組只可 import `adapters.base`。
  2. 每個模組以 `models.yaml` 設定可用模型;改模型清單不改程式。
  3. Web 後台建立/編輯成員以連動選單選 kind → provider → model,effort 只列模型支援的等級。
  4. 新模組必須通過 `tests/contract/` 的共用合約測試。
  5. 同一家 AI 的訂閱制 CLI 與 API 是不同模組(例:`claude_cli` 與 `anthropic_api`)。
  6. 每個模組在 manifest 宣告 `cardinality`:`single`(該 provider 只能有 1 個成員)或 `multiple`;訂閱 CLI 預設 single。
- 詳細契約:sdlc_docs/structure/design.md「Adapter 模組契約」、D11–D15。
- 原因:使用者要求不同的 AI 能以模組化方式加入專案,並在模組中配置可用模型、後台以選單選取;訂閱制 CLI 與 API 視為不同模組,模組可限定唯一或允許多個。
- 註記(2026-11-07,CHG-20261107-01,非規則):規則 1 將於 Rust 改寫 CHG 依 DIR-5 規則 4 ① 改寫,改寫前維持有效;同時要處理 AC-19、design D11。
- 註記(2026-11-08,CHG-20261108-01,非規則):上一則註記承諾的改寫改由設定檔驅動 adapter CHG 執行(CHG-20261108-01 決策 3、AM-17),AC-19、design D11 隨該 CHG 處理;該 CHG 合併前本條規則本文維持有效。
- 信度:使用者確認
- 狀態:生效

## DIR-4 — 測試、合回 main 與推送 origin 自動執行;只在分歧決策、需要密鑰或手動測試時停下
- 日期 / 分支:2026-11-01(UTC+0)/ all
- 情境:CHG 施工、逐 task review、驗收、合回 main 的各個停點。
- 規則:
  1. 測試(單元、合約、整合、behave、驗收測試、本機閘)與驗收流程一律自動執行,不另行詢問。
  2. CHG 驗收通過(ACC 結論為「通過」,或「部分通過」且未通過部分只剩待擁有者手動測試的項目)後,自動把 CHG 分支合回 main,並回填 CHG/ACC 的 Commit 欄;不再停下等使用者確認合併。
  3. 仍須停下交人的情況:(a) 分歧決策——有兩個以上合理選項、無法由文件或既有指示推導,照舊列選項與建議並詢問;(b) 需要真實密鑰或擁有者手動執行的測試(例如真實冒煙);(c) 永遠停點(不可逆刪除、付款、正式資料遷移、安全邊界變更,DIR-1 規則 4)。
  4. 合回 main(以及 main 上的治理 commit)後自動推送到 origin(2026-11-01 使用者追加);不 force push、不改寫已推送的歷史,推送被拒時停下回報。
- 與預設的差異(已揭露):預設中風險在合併前停、高風險每個停點都停;本條把「測試」「合回 main」「推送 origin」改為自動。高風險 CHG 的確認閘(開工前的使用者確認)與永遠停點不因本條放寬。風險:合回與推送前少一次人工把關,錯誤會直接進入公開 repo 的 main;回滾方式為 revert 該 CHG 的 merge commit 並推送(已推送的內容無法從他人取得的副本中撤回)。
- 原因:使用者指示「目前除遇到分歧決策和需要密鑰或手動測試,全部自動執行合併與測試」,並於同日追加推送也納入(Include push)。
- 信度:使用者確認
- 狀態:生效

## DIR-5 — 實作語言不限定 Python;保留 Python 版並新增 Rust 版,兩邊輸入輸出必須一致
- 日期 / 分支:2026-11-03(UTC+0)/ all;修訂 2026-11-07、2026-11-08
- 情境:選擇實作方式、新增模組或介面、撰寫測試時;任何可能把系統綁死在 Python 的設計決策。
- 使用者原話:「不限定 python,之後可以改用 rust;先把現在的需求處理完以後再評估 rust,最後才決定是否處理」(2026-11-03,開立 CHG-20261103-01 時)
- 使用者原話(2026-11-07):評估後選「Plan a Rust rewrite」;四項選擇為「Config-driven + built-ins」「Own clients + litellm price JSON」「Black-box tests first, then port」「Yes, pin first」;開發環境的 Python 版本選「Two locks」
- 使用者原話(2026-11-08,CHG-20261108-01):「保留python版本並增加rust版本 / 如果可以則共用測試單元 / 不行的話再各自獨立並且要求兩邊輸出輸入必須一致」。同日的問答(題目與所選,逐字):①「兩邊輸出要一致到什麼程度?」選項「語意一致」「逐位元組一致」,選「語意一致 (Recommended)」;②「adapter 擴充機制不同(Python 載入模組、Rust 讀設定檔),怎麼處理?」選項「兩邊都支援設定檔」「兩邊都只用設定檔」「各自保留」,選「兩邊都支援設定檔 (Recommended)」;③「送往 AI 供應商的請求(Python 用 litellm、Rust 自寫 client)要不要納入一致性比對?」選項「納入,語意比對」「不納入」,選「納入,語意比對 (Recommended)」;④「Rust 版還沒做完前,一致性怎麼要求?」選項「差距清單後追齊」「從現在起兩邊同步」,選「差距清單後追齊 (Recommended)」。決策審議後的問答(同日):範圍選「拆成三筆 (Recommended)」;log 比對選「不比事件內容 (Recommended)」;cli 協定選「封閉方言 (Recommended)」;首次建置選「你親自執行 (Recommended)」。
- 規則:
  1. 實作語言不限定 Python。2026-11-08 起方向為保留 Python 版並新增 Rust 版,Python 版不退役;測試能共用則共用,不能共用則各自獨立,且兩邊輸入輸出必須一致(spec 第 15 節,CHG-20261108-01 決策 1)。歷史:2026-11-07 擁有者曾決定規劃改寫,終點為 Rust 版通過同一套測試後 Python 版退役,已由 2026-11-08 的決定取代。
  2. 三段順序:① 完成現有需求 → ② 評估改用 Rust → ③ 由使用者決定是否處理。順序不可跳過或對調。(② 已完成,2026-11-07,評估報告 `rust-evaluation.md`;③ 擁有者 2026-11-07 決定規劃改寫,2026-11-08 改為保留 Python 版並新增 Rust 版)
  3. Rust 骨架 CHG 開立前,不新增 Rust 程式碼或建置流程。鎖定相依(CHG-20261107-01)、測試黑箱化與差分管線(CHG-20261108-01,第二實作為包裝 Python 的突變 wrapper)不算新增 Rust。
  4. Rust 版的四項選擇(使用者 2026-11-07 為改寫所選,2026-11-08 起適用於新增的 Rust 版):① adapter 擴充採設定檔驅動加內建 adapter;② 自寫 HTTP client,價格與 context 表沿用 litellm 的 JSON;③ 先把測試改為黑箱再移植;④ 先鎖定相依。① 的修正(2026-11-08,擁有者選「兩邊都支援設定檔」):兩個實作都支援設定檔,Python 模組載入保留為 Python 專屬,由設定檔驅動 adapter CHG 施作。
  5. (a) 過渡期只有變更 `rust/` 或 §15 的 CHG 必須跑雙實作閘;(b) 差距清單清空(決策 5 的「追齊」定義)後,會改變程式或測試行為的 CHG 必須跑,純文件 CHG 與 DIR-4 規則 4 的治理 commit 不在此限;(c) 找不到 cargo 或 binary 判失敗,不得略過,屬 DIR-4 規則 3(b) 停點;(d) 只有一邊通過,不得成為 ACC「通過」或「部分通過」;(e) 單側緊急修補的例外在清單清空前由擁有者決定,在此之前沒有例外。
- 規則 5 的出處:CHG-20261108-01「本機閘」節;其中「決策 5」指該 CHG 決策 5 的「追齊」定義(`tests/parity/rust_gaps.toml` 清空,且 `impl_dependent.toml` 的 `on_rust = replace` 都有替代測試、spec 第 15 節狀態表沒有待定義列)。
